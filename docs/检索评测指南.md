# 菜谱 RAG 检索评测指南

本文档说明 cook-rag 项目中**检索评测**的完整流程：从评测数据集的构建，到评测指标的实现，再到三路检索对比与专项评测。阅读本文后，你可以独立运行评测并理解报告中的每个数字。

---

## 一、整体流程

检索评测分为两个阶段，分别由两个脚本驱动：

```
┌─────────────────────────────┐      ┌──────────────────────────────────┐
│  阶段一：生成评测数据集      │      │  阶段二：执行检索评测             │
│  build_eval_dataset.py      │ ───▶ │  run_retrieval_eval.py           │
│                             │      │                                  │
│  菜谱 md ──解析──▶ 评测样本  │      │  评测样本 + 检索系统 ──▶ 指标报告  │
└─────────────────────────────┘      └──────────────────────────────────┘
        产出 data/eval/*.jsonl              产出 reports/retrieval_eval_report.json
```

- **阶段一**不依赖向量索引、LLM 或 API Key，纯标准库实现，可独立运行。
- **阶段二**需要构建检索系统（加载 embedding 模型与 FAISS 索引），但同样不初始化 LLM、不需要 DeepSeek API Key。

运行环境：项目自带 venv `cook-rag-1/Scripts/python.exe`（Python 3.12.7，依赖齐全）。

## 二、评测数据集生成

### 2.1 为什么需要评测集

RAG 系统的检索质量无法靠"试几个问题感觉一下"来衡量。需要一套**带标准答案的查询集**，才能量化"检索到了没有""排第几""前 k 个里有没有正确结果"。本项目的标准答案来自菜谱数据本身——每个 `.md` 文件的元数据（分类、难度、菜品名）天然就是 ground truth。

### 2.2 数据集结构

评测集存放在 `data/eval/` 目录，共三类：

| 文件 | 条数 | 用途 |
|---|---|---|
| `retrieval_eval.jsonl` | 345 | 检索评测（query → 相关文档） |
| `generation_eval.jsonl` | 40 | 生成评测（query → 参考答案） |
| `robustness_eval.jsonl` | 15 | 鲁棒性评测（越界/歧义/空结果） |

本文聚焦检索评测，其每条样本的字段如下：

```json
{
  "id": "ret_001",
  "query": "水煮鱼怎么做",
  "query_type": "detail",
  "relevant_doc_ids": ["aquatic/水煮鱼.md"],
  "hard_negatives": ["aquatic/清蒸鲈鱼.md", "aquatic/红烧鱼.md"],
  "filters": null,
  "note": "具体菜品制作方法",
  "source_dish": "水煮鱼"
}
```

| 字段 | 说明 |
|---|---|
| `query` | 用户查询文本 |
| `query_type` | 路由类型：`detail`（具体菜品）/ `list`（推荐列举）/ `general`（信息咨询） |
| `relevant_doc_ids` | 正确答案：相关文档的 doc_id 列表 |
| `hard_negatives` | 同分类易混淆菜品（易被误召回），用于分析 |
| `filters` | 元数据过滤条件（如 `{"category":"水产"}`），list 类查询携带 |
| `source_dish` | 来源菜品名（list 类为 null） |

> **doc_id 约定**：相对 `data/cook/dishes` 的 posix 路径，如 `aquatic/水煮鱼.md`。这是全链路匹配的统一标识。

### 2.3 生成脚本设计（`build_eval_dataset.py`）

脚本采用**半自动**策略：从菜谱元数据自动生成候选，再由人工微调。

**步骤 1：解析菜谱**。遍历 `data/cook/dishes` 下所有 `.md`（排除 `template` 目录），用正则提取：
- 菜名（`# X的做法` / 文件名）
- 分类（路径中的目录名 → `CATEGORY_MAPPING` 映射，与 `data_preparation.py` 一致）
- 难度（`预估烹饪难度：★+`，★数 → 非常简单~非常困难）
- 食材清单、用量、营养表（按 `##` 标题分段提取）

**步骤 2：按分类采样**。每个分类采样 8 个菜品（`--per-category` 可调），保证 10 个分类全覆盖。固定随机种子（`--seed`，默认 42）保证可复现。

**步骤 3：用模板生成 query**。对每个采样菜品，套用三类模板：

| 路由类型 | 模板示例 | 数量 |
|---|---|---|
| detail | `{菜名}怎么做` / `{菜名}的制作方法` / `{菜名}需要什么食材` | 3 条/菜 |
| general | `{菜名}的营养价值` | 1 条/菜 |
| list | `推荐几个{分类}菜` / `有什么{分类}` / `给我几个{难度}的菜` | 每分类 2 条 + 每难度 1 条 |

**步骤 4：构造 hard negatives**。对每条 detail/general 查询，从同分类下取 2-3 个其他菜品作为易混淆负样本。

**步骤 5：鲁棒性样本手工设计**。覆盖越界查询（拒答）、不存在菜品（空结果）、歧义查询（追问）、健康咨询等 15 条。

### 2.4 运行方式

```bash
# 默认每分类采样 8 个，seed=42
cook-rag-1/Scripts/python.exe build_eval_dataset.py

# 自定义参数
cook-rag-1/Scripts/python.exe build_eval_dataset.py --per-category 12 --seed 42
```

### 2.5 生成结果统计

运行后输出（保存在 `data/eval/eval_stats.json`）：

```
共 322 个菜谱，采样 80 个
检索评测: 345 条 (detail=240, list=25, general=80)
生成评测: 40 条
鲁棒性:   15 条
```

## 三、检索评测过程

### 3.1 评测指标说明

评测器（`MetricsCalculator`）计算 5 个核心指标，全部基于**二值相关性**（文档要么相关、要么不相关）：

| 指标 | 含义 | 直观理解 |
|---|---|---|
| **Recall@k** | 前 k 个结果中命中的相关文档 / 全部相关文档 | "该找到的找到了多少" |
| **Precision@k** | 前 k 个结果中相关的比例 | "找到的里面有多少是对的" |
| **MRR** | 第一个相关结果的倒数排名（1/排名） | "正确结果排第几" |
| **NDCG@k** | 考虑排序位置的相关性增益（归一化） | "排得准不准" |
| **HitRate@k** | 前 k 个是否至少命中一个（0/1） | "有没有命中" |

其中 MRR 不依赖 k，反映整体排序质量；其余指标在多个 k 值（1/3/5）下计算，观察"给多少候选"对效果的影响。

### 3.2 三路检索对比设计

项目的 `RetrievalOptimizationModule` 实现了三路检索，评测器对**同一条 query** 分别跑三路，横向对比：

| 路由 | 实现 | 说明 |
|---|---|---|
| `vector` | FAISS 向量相似度检索（BGE-small-zh） | 语义匹配 |
| `bm25` | rank_bm25 关键词检索 | 字面匹配 |
| `hybrid` | RRF 融合 vector + bm25（与项目现有逻辑一致） | 混合检索 |

为支持任意 top_k 评测，评测器内部用 `pool_size=50` 的候选池：向量检索取前 50、BM25 取前 50，RRF 在此范围内融合后截断到 k。这比项目原有的"两路各取 5"更公平，能评测更大的 k。

### 3.3 专项评测

除三路对比外，评测器还做两项针对项目架构的专项评测：

**父子文档召回**：项目的检索返回的是子块（按标题切分），但最终喂给生成模块的是父文档（整篇菜谱）。所以"父文档是否被正确取回"比"子块是否命中"更关键。该指标对 detail 类查询统计：子块命中后，`get_parent_documents` 是否取回了正确父文档。

**元数据过滤准确率**：对携带 `filters` 的 list 类查询，统计 `metadata_filtered_search` 返回的结果是否都满足过滤条件（如分类=水产）。反映过滤逻辑的正确性。

### 3.5 运行方式


## 四、评测结果与关键发现

以下是 345 条样本、k=[1,3,5] 的实测结果。

### 4.1 三路检索对比（detail 类，240 条）

| 指标 | vector | bm25 | hybrid |
|---|---|---|---|
| recall@1 | **0.983** | 0.000 | 0.621 |
| recall@3 | **1.000** | 0.000 | 0.858 |
| hit_rate@3 | **1.000** | 0.000 | 0.858 |
| mrr | **0.989** | 0.000 | 0.701 |

向量检索几乎完美，BM25 全线归零，RRF 混合被 BM25 拖累。

### 4.2 关键发现

**发现一：BM25 在中文场景下完全失效**
`rank_bm25` 默认按空格分词，而中文没有空格。"水煮鱼怎么做"被当作单个 token，无法匹配文档里的"水煮鱼"。这导致 BM25 的所有指标接近 0。

**发现二：当前 hybrid 不如纯 vector**
由于 BM25 提供的是噪声而非信号，RRF 融合后 hybrid 的 recall@1（0.62）远低于纯 vector（0.90）。即"混合检索"在当前实现下帮了倒忙。

**发现三：父子文档召回有 14% 丢失**
父子文档召回 HitRate@3 = 0.858，意味着约 14% 的查询子块命中后，父文档未被正确取回，这些查询最终会拿到错误或缺失的菜谱。

**发现四：元数据过滤准确率仅 75%**
25% 的过滤查询返回了不满足条件的文档，说明 `metadata_filtered_search` 存在边界问题（可能是部分文档 metadata 字段缺失或值不一致）。

### 4.3 评测过程中修复的 bug

1. **`data_preparation.py:191` 拼写错误**：`startwith` → `startswith`。这是项目原生 bug，导致所有菜谱 Markdown 分割失败（每个菜谱作为一个整块，分块数 = 文档数）。修复后分块数 **323 → 2086**（按标题正确切分），旧索引已删除重建。
2. **eval 文件格式兼容**：评测集文件被 IDE 格式化成多行 JSON，评测脚本的加载函数改用 `JSONDecoder.raw_decode` 逐对象解析，兼容单行 jsonl 与多行 pretty-print 两种格式。

## 五、后续优化方向

按收益排序：

1. **给 BM25 接入中文分词**（jieba）：`BM25Retriever` 支持自定义 `preprocess_func`，分词后 BM25 才能真正贡献信号，RRF 才有意义。改完重跑评测即可验证 hybrid 是否反超 vector。
2. **排查元数据过滤的 25% 失败**：检查失败案例中文档的 `category`/`difficulty` 字段是否缺失或值不匹配。
3. **排查父子召回的 14% 丢失**：检查 `get_parent_documents` 的去重与排序逻辑边界情况。
4. **进入 P1 生成评测**：RAGAS 忠实度、答案相关性，以及查询路由准确率。
